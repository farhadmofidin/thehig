An AMS-like Rental Platform
Architecture Design

A cloud rental system where physical machine usage flows from device to invoice. Scoped to one branch, with the hard differentiators built in-house: native GPS/usage telematics and metered pay-per-use billing.

◆ Native telematics ◆ Pay-per-use billing ● Single branch ○ Accounting: pluggable, deferred

01What the scope decisions fix

Four answers turn an open-ended "rebuild AMS" into one concrete building. Each removed or kept a whole subsystem.

Native telematics → kept

A separate ingestion service + a time-series store become non-negotiable. This is the one seam worth splitting out of the monolith on day one — its scaling and failure profile are nothing like the ERP's.

Pay-per-use → kept

The biggest consequence: billing correctness now depends on sensor-data correctness. The rating engine stops being a pure function of dates and starts consuming noisy physical reality.

Single branch → simplify

Drop cross-branch transfers & consolidation. But keep org_id/branch_id on every row — one column now is the difference between "add branches later" being additive vs. a rewrite.

Accounting → deferred

Don't block on the ERP choice. Define a LedgerExport port now, ship CSV/PDF export, drop an Exact/Twinfield/SAP adapter in behind the same interface later.

By choosing native telematics + pay-per-use you took on the moat — the hard, differentiating engineering — while skipping the boring scale complexity. Most of the project's risk and value now live in one pipeline: device → usage → invoice.

02System shape — monolith + one ingestion service

Not microservices. Two deployables, joined by an event stream. The ERP modules share too many transactions to split early; telematics is genuinely independent, so it gets its own service.

04Three rules that prevent the classic disasters

Pay-per-use kills projects in predictable ways. These three design decisions defuse each one.

Temporal attribution is a clean join

A reading belongs to whatever contract owned that asset at that timestamp. The contract spine already models [start,end) with tstzrange — so "who owned asset X at time T" is a one-line range query. Your state machine and your billing attribution are the same mechanism.

Raw ≠ billable

Raw telemetry is immutable truth. Usage windows are a projection you can recompute, version, and dispute. When a customer challenges an invoice, you replay raw → usage and show your work. Disputes become resolvable instead of arguments.

Gaps get flagged, never zero-billed

A 6-hour telemetry blackout is a business decision — estimate? exclude? ask the customer? — surfaced for review, not a silent 0 that quietly erodes trust in the entire invoice.

All three lean on the same backbone: an explicit contract state machine with tstzrange periods. That one decision prevents double-booking and drives usage attribution — build it first.

06Build order — forced by the dependency, and it's a gift

Because billing now depends on telemetry, you must build bottom-up — and that order happens to de-risk the project for you.

Contract spine + booking

The temporal backbone. tstzrange exclusion = no double-booking and the usage-attribution join key, for free.

Time-based billing — prove it against real invoices

Price by period + scales + surcharges + tax. Validate against the client's existing AMS invoices. Deterministic, documented, self-checking. Get a billing engine you fully trust before sensor data goes near it.

Telematics ingestion

Raw readings flowing in, attributed to assets and contracts. No billing yet — just trustworthy data.

Usage derivation + pay-per-use rating

Layer metered usage on top of a billing engine you've already verified. Never build deterministic and metered billing at the same time.

08The one risk — and how to retire it first

Native telematics + pay-per-use put most of the project's risk and most of its value into the same pipeline. That's fine — it just tells you exactly where to aim the first proof.

Vertical-slice proof: one device → raw readings → a usage window → a rated line → an invoice that matches what the client would have billed in AMS. Nail that thin end-to-end slice and you retire ~70% of the project's real uncertainty in the first stretch.
Safe & self-checking

Time-based billing — validated against existing invoices.

Well-trodden

Catalog, contracts, portal, planning board.

The frontier

Ingestion + usage derivation + pay-per-use rating.
